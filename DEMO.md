# Инструкция по проверке и демонстрации (DEMO.md)

В данном документе описаны команды и сценарии для проверки всех обязательных требований технического задания сервиса контроля времени ответа (SLA Service).

---

## 🚀 1. Развертывание и запуск (Сценарий поставки)

> **Требование ТЗ**: Чистая машина с Docker должна поднять приложение и PostgreSQL по инструкции без ручного создания таблиц.

```bash
# 1. Клонирование и переход в директорию
git clone <repository_url>
cd test_time

# 2. Подготовка переменных окружения
cp .env.example .env

# 3. Сборка и запуск всех контейнеров одной командой
make up
# или: docker compose up --build -d
```

### Доступ к сервисам:
- **Веб-интерфейс**: [http://localhost:3000](http://localhost:3000)
- **FastAPI Документация (Swagger)**: [http://localhost:8000/docs](http://localhost:8000/docs)
- **Health Check**: [http://localhost:8000/health](http://localhost:8000/health)

## 🔍 3. Проверка обязательных сценариев вручную через cURL / CLI

### Сценарий 1: Идемпотентность при конкуренции
> **Требование ТЗ**: Отправьте 20 одинаковых событий клиента параллельно. В БД и в списке открытых обращений должно остаться ровно одно обращение.

Запустите 20 параллельных запросов с одинаковым `external_event_id`:

```bash
for i in {1..20}; do
  curl -s -X POST http://localhost:8000/api/events \
    -H "Content-Type: application/json" \
    -d '{
      "external_event_id": "evt_concurrent_demo_01",
      "event_type": "client",
      "external_client_id": "client_tg_001",
      "topic": "Техническая поддержка",
      "content": "Сообщение о проблеме с авторизацией"
    }' &
done; wait
```
**Результат**: ровно один запрос вернет `201 Created`, остальные 19 вернут `200 OK` (дедупликация `ON CONFLICT DO NOTHING`). В списке `/api/tickets` будет ровно 1 тикет.

---

### Сценарий 2: Корректная параллельность (неблокирующий Event Loop)
> **Требование ТЗ**: В тестовой реализации адаптера уведомлений добавьте задержку 1–2 сек. Пока уведомление отправляется, `GET /health` и `GET /api/tickets` должны отвечать мгновенно.

```bash
# Проверка времени ответа health check (должен отвечать за < 10 мс)
curl -w "\nВремя ответа: %{time_total}с\n" -s http://localhost:8000/health

# Проверка списка тикетов
curl -w "\nВремя ответа: %{time_total}с\n" -s http://localhost:8000/api/tickets
```
**Что обеспечивает это свойство**:
1. Асинхронный неблокирующий I/O (FastAPI + asyncpg).
2. Фоновая отправка нотификаций вынесена в отдельный фоновый процесс `worker` (Transactional Outbox).
3. Адаптер использует `await asyncio.sleep(...)`, не блокируя основной Event Loop.

---

### Сценарий 3: Защита от повторных алертов
> **Требование ТЗ**: Повторный запуск проверки SLA не создаёт второй warning или overdue для того же обращения. При переходе warning → overdue создаётся одно новое уведомление.

- Создайте тикет. Через 60 секунд SLA Sweeper переведет его в статус `warning` и запишет 1 событие в `outbox_events`.
- Повторные циклы проверки (каждые 5 сек) **не будут** создавать дублирующие записи.
- По истечении 180 секунд тикет перейдет в `overdue`, создав ровно 1 новое уведомление `sla_overdue`.

---

### Сценарий 4: Атомарность при сбоях
> **Требование ТЗ**: При сбое между обработкой события и созданием сущности транзакция откатывается; повторная доставка приводит систему в корректное состояние.

Проверяется автоматическим тестом:
```bash
pytest backend/tests/test_atomicity.py -v
```

### Сценарий 5: Расчет метрик и медианы на уровне СУБД
> **Требование ТЗ**: Эндпоинт метрик возвращает корректные агрегированные показатели и медиану, включая пустую выборку.

```bash
curl -s http://localhost:8000/api/metrics | jq .
```
Пример ответа:
```json
{
  "total_created": 3,
  "total_answered": 1,
  "total_overdue": 0,
  "median_first_response_time_seconds": 42.5,
  "period_from": null,
  "period_to": null
}
```
